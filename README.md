# FTFL contract engine

Real contract data for all 10 teams, each team's page themed in that
team's actual colors, a league summary view, and — new this round — a
real backend: commissioner login + edit screen backed by Vercel KV, and a
Fleaflicker proxy for live scores/standings.

**Important:** the commissioner login and Fleaflicker standings only work
once this is deployed on Vercel with the setup below done. Running `npm
run dev` locally (plain Vite) renders the UI fine but the `/api/*` routes
don't exist in that mode — logins will fail and Fleaflicker will show
dashes. Use `vercel dev` (see below) to test the backend locally, or just
deploy and test on the real URL.

## Run it locally (frontend only)

```
npm install
npm run dev
```

## Run it locally with the backend (recommended before you rely on it)

```
npm install -g vercel
vercel dev
```

This runs the `/api` functions locally too, so login and saving actually
work. It'll ask you to link the project to Vercel the first time.

## One-time setup on Vercel

1. **Add a KV database.** In your Vercel project → Storage tab → Create
   Database → KV. Vercel wires the connection env vars in automatically —
   you don't set those by hand.
2. **Set `COMMISSIONER_PASSWORD`.** Project Settings → Environment
   Variables → add `COMMISSIONER_PASSWORD` with whatever password you want
   to use to log in. Never commit this to the repo.
3. **Set `FLEAFLICKER_LEAGUE_ID`** (for live scores/standings). Open your
   league on fleaflicker.com — the URL looks like
   `fleaflicker.com/nfl/leagues/XXXXXX` — that number is the league ID.
   Add it as an env var of the same name.
4. Redeploy after adding env vars (Vercel doesn't hot-apply them to an
   already-running deployment).

## How the data flows now

- On load, the app instantly renders the bundled seed data
  (`src/data/realContracts.ts`) so there's no blank-loading flash, then
  quietly fetches `/api/contracts` and swaps in whatever's actually in KV.
  First time ever, KV is empty, so the API itself falls back to serving
  the seed data — from that point on, KV is the real source of truth.
- The **commissioner screen** (log in via the button top-right of the team
  rail) lets you edit position, toggle taxi/IR for the year you're
  viewing, cut a player, or add a new contract. Nothing is saved to the
  server until you click "Save to server" — up until then it's just local
  state, so you can experiment freely before committing.
- **Auth is intentionally simple**: one shared password in an env var,
  checked server-side on every write. Good enough for "only the
  commissioner edits this," not a real multi-user permission system.

## What's real vs. generated

- `src/lib/contracts.ts` — the confirmed rules: new contracts escalate
  by tier at signing (under $10 → +$2/yr, $10–29 → +$3/yr, $30+ →
  +$5/yr); cutting a player costs 50% of their current salary, applied
  across every remaining contract year, rounded up once at the end (see
  the "Cut penalty — corrected" section below for the fix history); taxi squad and IR don't count against the $200 cap;
  "resign" cost projects the final rate forward using that rate's
  increment for as many years as the player's been held at it.
- `src/data/realContracts.ts` — generated by `scripts/import-from-excel.py`
  from `FTFL_Dynasty_League.xlsx`. This is now just the SEED for KV, not
  the live source once you've saved anything through the commissioner
  screen.
- `src/data/teams.ts` — every color is a raw hex value read directly off
  the workbook's actual cell fills and font colors (via `openpyxl`), not
  adjusted or brightened. A couple of teams' real accent color only shows
  up as font color, not fill (Denver's green, for example) — worth
  knowing if you ever re-run the extraction for a team that looks off.

## Cut penalty — corrected

Fixed. Cutting a player costs 50% of their CURRENT salary (the rate in
the year of the cut), applied flatly across every remaining contract
year, with ONE rounding at the end — not the escalating future rate for
each year, each rounded separately. Example: a $5 current salary with 1
year remaining → ceil(5 × 0.5 × 1) = $3. See `cutPenalty` in
`src/lib/contracts.ts`.

## The manual workflow, end to end

Since Fleaflicker trades/cuts/taxi/IR aren't auto-applied (see above),
here's what actually needs to happen when something happens in
Fleaflicker:

1. Log in as commissioner.
2. Go to the team page for whoever's affected, click "Edit roster."
3. **Cut** → click Cut next to that player.
4. **Trade** → pick the receiving team from "Trade to…" next to that
   player. Do this once per player moving (a 3-for-2 trade is 5 clicks,
   not one "propose trade" flow — there's no multi-asset trade builder
   yet).
5. **Taxi/IR move** → click Taxi or IR next to that player for the year
   you're viewing.
6. **New free agent signing with a cost** → use the FA Review page
   instead (it's built for this specifically) or "Add contract" at the
   bottom of the team page.
7. Click **"Save to server"** — nothing above persists until this is
   clicked. You can make several changes across the same edit session
   before saving once.

## Fleaflicker schema — now confirmed against real data, not guessed

Nick pasted a live response from `/api/FetchLeagueTransactions`. Two big
findings:

1. **Field names are camelCase over the wire** (`timeEpochMilli`,
   `recordOverall`, `proPlayer`, `nameFull`) even though Fleaflicker's own
   docs describe them in snake_case (`time_epoch_milli`,
   `record_overall`). This is a standard protobuf-JSON quirk — the docs
   show the underlying proto field name, but serialization auto-converts
   to camelCase. **This means `fetchFleaflickerStandings` was broken from
   the start on a naming mismatch** — fixed now, so Record/PF on the
   League Summary page should actually populate.
2. **Confirmed drop detection.** A dropped player shows up as
   `item.transaction.type === "TRANSACTION_DROP"` with the player at
   `item.transaction.player.proPlayer.nameFull` and the team at
   `item.team.name` (a sibling of `transaction`, not nested inside it).
   The FA Review page now shows a "Confirmed drops" section — any
   Fleaflicker drop that matches an existing contract gets a one-click
   "Confirm cut" button.

**Still not confirmed:** the exact `type` string for an add (no example
came through in the sample), and whether trades show up as a clean event
at all — several items in the sample had a player + an `owner` field but
no `type`, which look like "this player is on X's trade block" context
rather than a completed trade. Those are filed under "Other recent
activity," not acted on. If a real trade shows up in that section with a
recognizable shape, send it over and trade auto-detection can get built
properly instead of guessed.

No bid/waiver-cost field appears anywhere in the real data, matching what
Nick said — this league prices FAs outside Fleaflicker. The FA-add form
no longer pretends to pre-fill a cost from Fleaflicker.

## Trades, cuts, taxi/IR — now fully automatic (one button, not per-item)

New: `api/sync.ts` + a "🔄 Sync trades / cuts / taxi / IR" button on the
FA Review page. One click reconciles every contract against Fleaflicker's
CURRENT rosters — not by reading an event log and guessing what it means,
but by comparing "what does my data say" against "what does Fleaflicker
say right now":

- Player not on ANY team's roster anymore → **cut** (contract removed).
- Player on a different team than my records show → **traded** (contract
  reassigned, same salary/years intact).
- Player in Fleaflicker's TAXI or INJURED roster slot → **taxi/IR flag**
  set or cleared for the year being synced.

No per-player confirmation — it applies everything and saves immediately,
then shows a plain-text summary of what changed. FA pickups are the only
thing still requiring you: Fleaflicker has no price data for adds in this
league, so those still show up below as a manual "enter a cost" form.

**Confidence level, honestly:** the "cut" and general approach reuse the
confirmed FetchLeagueTransactions schema from before. The roster
reconciliation (`FetchLeagueRosters`, in `api/sync.ts`) is built by
extending a schema I DID confirm for a single team (`FetchRoster`) to its
all-teams sibling, which was never seen in a real response — it's a
well-grounded guess, not a wild one, but it's the one part of this whole
project that's still unverified against live data. If you click Sync and
it always reports zero changes even when you know a trade or cut just
happened, that's the first thing to check: hit
`/api/fleaflicker?endpoint=FetchLeagueRosters` directly in your browser
and send me what comes back — same as the transactions fix, this is a
five-minute correction once I can see the real shape instead of a

## Incident: sync mass-cut the whole league — fixed with real safety guards

What happened: the `FetchLeagueRosters` schema in `api/sync.ts` was always
labeled as an unverified guess (see the comment above `fetchRosterMap`),
and it turned out to be wrong — the roster map came back empty, and the
code treated "no match found" as "this player isn't rostered anywhere,"
cutting every single contract in the league in one sync. That's a real
failure of judgment on my part: an unverified data source should never
have been allowed to drive a fully-automatic destructive action with no
circuit breaker. Fixed properly now, not just patched:

1. **Guard #1 — empty/near-empty roster data refuses to run at all.**
   If Fleaflicker's response produces fewer than 5 recognizable players,
   `api/sync.ts` aborts before touching any data and returns the raw
   response sample in the error, so the actual shape is visible instead
   of guessed at again.
2. **Guard #2 — implausible cut ratio refuses to save.** Even with a
   healthy-looking roster map, if the computed result would cut more
   than 25% of the active roster in one pass, the sync aborts and lists
   which players it would have cut, instead of saving. A real week never
   looks like this; a name-matching bug sometimes does.
3. **`api/restore-seed-data.ts` — new emergency recovery endpoint.**
   Visiting `/api/restore-seed-data` in a browser wipes whatever's in
   Redis and replaces it with the original spreadsheet import. Bookmark
   this. It's the fast way back to a known-good state if anything ever
   corrupts live data again, without needing to find Upstash's console
   under time pressure.

The underlying schema question — what `FetchLeagueRosters` actually
returns — is still unconfirmed. These guards mean that not knowing is
now safe to find out (it aborts loudly instead of failing destructively),
but the root cause fix still needs a real response sample. If Sync ever
refuses to run and shows a "raw sample" in the error, that's the payload
to send over.

## Roster schema — now confirmed for real (cuts/trades), taxi/IR still a guess

The safety guard did its job: it refused to run on bad data and surfaced
a real sample instead. Turns out `FetchLeagueRosters` has no
groups/slots nesting at all — it's flat: `{ rosters: [{ team, players:
[{ proPlayer: { nameFull, ... } }] }] }`. Fixed `fetchRosterMap` in
`api/sync.ts` to match this confirmed shape. Verified directly against
Nick's real sample (Jordan Love → Boulder Bandits) before shipping —
this part is no longer a guess.

**Taxi/IR is still unconfirmed** — the sample was truncated before
reaching whatever field marks a player as taxi-squad or IR on this
endpoint. Current code checks a few plausible field names
(`rosterSlot.name`, `slot.name`, `status`, `isTaxi`, `isInjuredReserve`)
and safely defaults to "neither" if none match — so it won't wrongly tag
anyone, it just might not catch a real taxi/IR move yet. If Sync doesn't
seem to be picking up a taxi/IR change you know happened, that's the
next thing to nail down — ideally with one more real sample of a player
who's actually on taxi or IR right now, so the differentiating field is
visible in full (not truncated).

## Second incident: suffix mismatches wrongly cut real players

The roster schema fix was correct, but name matching itself was too
strict — a plain lowercase/trim comparison, which fails whenever the two
sources format a suffix differently ("Michael Pittman Jr." vs "Michael
Pittman"). This wrongly cut several real, actively-rostered stars
(Mahomes, Pittman, Etienne, Penix, Walker) even though the 25% safety
threshold didn't trigger (real drops mixed in with the false positives
kept it under the line).

Fixed in both `api/sync.ts` and `src/App.tsx` (FA Review's contract
matching): `normalize()` now strips periods/commas/apostrophes, accents,
and generational suffixes (Jr/Sr/II/III/IV) entirely from both sides
before comparing, verified against every false-positive name from the
actual incident before shipping.

**Worth considering, not yet built:** given two real incidents from two
different root causes, a "review cuts before saving" confirmation step
(cuts only — trades/taxi/IR are non-destructive and can stay fully
automatic) would add a safety checkpoint against whatever the next
unforeseen name-matching edge case turns out to be, at the cost of one
extra click when a cut is real. Worth deciding on deliberately rather
than defaulting to full-auto by inertia.

## Third incident, and the real fix: cuts are no longer automatic

Two things went wrong in the same sync run:

1. **Taxi/IR detection was actively erasing real data.** The guessed
   field names for taxi/IR status never matched anything real, so
   `isTaxi`/`isIR` always computed to `false` — which meant every
   legitimate taxi player got read as "not taxi" and had their flag
   removed on every single sync. **Taxi/IR detection is now removed
   entirely** (not just "safer," gone) until a real sample confirms the
   actual field. Set taxi/IR manually on the team page for now.
2. **A genuinely-still-rostered player (Jacoby Brisset) came back
   missing from Fleaflicker's roster data**, and got treated as a cut.
   This isn't the suffix bug — likely the endpoint doesn't return full
   benches, or needs a parameter this code isn't passing. Root cause
   still open.

Given "not found on any roster" has now caused real damage from two
unrelated causes, the actual fix is architectural, not another patch:
**cuts are no longer applied automatically at all.** `api/sync.ts` still
computes them, but only returns them as proposals — nothing is removed
until the commissioner clicks "Confirm cut" on the FA Review page for
that specific player, with a "not a real cut, ignore" option right next
to it for false positives. Trades stay automatic (wrong trades are
easily fixed manually; lost contract data isn't).

This is the actual permanent guard, not a promise to be more careful
next time: no code change can silently delete a contract again, because
the deletion now requires a human clicking a button that names the
specific player.

## Taxi/IR — still genuinely unresolved, and here's exactly why

Went through the full roster dump specifically looking for a current-
taxi/current-IR field on each player. It isn't there. Every player has
an `eligibleFor` array listing what slots they're ELIGIBLE to occupy
(and it turns out nearly every player is taxi-eligible and every injured
player is IR-eligible) — but nothing on this endpoint says which slot
they're ACTUALLY in right now. Eligible-for isn't the same as
assigned-to, and this bulk, all-teams endpoint doesn't expose the
assignment at all.

The single-team endpoint (`FetchRoster`, needs a `team_id`) is
officially documented to return `groups: [{ group: "TAXI"/"BENCH"/
"START"/"INJURED", slots: [...] }]` — actual current placement, not
eligibility. That's the right endpoint for this; the docs schema was
already confirmed by Fleaflicker, it just hasn't been tested against a
real response yet. Now that real fleaflickerId values exist in
teams.ts, this is a straightforward next step: fetch
`FetchRoster?sport=NFL&league_id=245051&team_id=1417685` (Boulder
Bandits, Nick's own team — likely to return full detail since he's
authenticated as its owner) and confirm the shape before wiring it up,
same discipline as everything else in this file.

## Taxi/IR automation reverted — real wall found, not a bug to patch

The confirmed `FetchRoster` schema from the last round was real, but the
endpoint itself turned out to require an authenticated Fleaflicker
session. Proof: the exact same team_id that worked when Nick fetched it
from his own logged-in browser (Boulder Bandits, 1417685) returned

Fleaflicker's public/anonymous endpoints (`FetchLeagueStandings`,
`FetchLeagueTransactions`, `FetchLeagueRosters`) all keep working fine —
this one specific endpoint just isn't reachable from an unauthenticated
server. Reverted `api/sync.ts` to the bulk `FetchLeagueRosters` endpoint
only (proven: 232/232 contracts matched against real data). Trades and
cut-proposals work exactly as before. **Taxi/IR is back to manual, on
the team page**, and stays there unless a way to authenticate this
server as a real Fleaflicker session shows up — that would need
something like a stored API token or session cookie Fleaflicker doesn't
appear to offer for this purpose.

## Taxi/IR — solved for real, via the activity feed (not FetchRoster)

After the login wall killed the `FetchRoster` approach, reading the
*entire* API docs page top to bottom (not just the endpoints already in
use) turned up `FetchLeagueActivity` — public, no login, and its
`reserveChange` items log every taxi/IR move.

Fleaflicker's JSON encoding omits boolean fields when they're `false`
(standard protobuf JSON behavior), so a `reserveChange` item's shape
*is* the event:
- no `taxi`, no `removed` → added to **IR**
- `taxi: true`, no `removed` → added to **TAXI**
- `removed: true`, no `taxi` → removed from **IR** (activated)
- `removed: true, taxi: true` → removed from **TAXI** (promoted)

Verified against 11 real players in a real feed response before this
was wired in — e.g. A.J. Brown's real NFL IR designation lines up with
a bare add-to-IR event; Denzel Boston and Harold Fannin, both real
active contributors now, show promoted-off-taxi events. All 11 matched.
Also verified the "latest event wins" logic against a player (Alec
Pierce) with two conflicting historical events, correctly resolved by
timestamp.

`api/sync.ts` now fetches this activity feed (paginated, fetched in
parallel rather than sequentially since a league can have 1000+ items)
alongside the existing bulk roster endpoint, and computes each player's
current taxi/IR status from their most recent `reserveChange` event.
**Trades and taxi/IR are both automatic now.** Cuts remain proposals —
that stays true regardless of how solid the rest of this gets.

## Cuts are buyouts now, not deletions

Confirmed rule change: a cut no longer removes the contract. It converts
into a `BuyoutContract` — same player, same team, but with an explicit
per-year cost schedule: for every year that would have remained on the
original deal, the buyout owes 50% of THAT year's own contracted salary,
rounded up separately for each year (a $5 year becomes a $3 buyout year
on its own — confirmed against Nick's exact example). This is a real
change from the old rule, which took the flat current-year salary and
applied it across all remaining years with one rounding at the end;
the new per-year rule can total meaningfully more on an escalating deal.

## Top scorers, attempt 4: a string/number mismatch, not a wrong field

The `game` wrapper fix was actually correct — the diagnostic samples
confirmed team identity really does live at `box.away.id` /
`box.home.id`. But totals were still all zero. The real remaining bug:
`knownIds` is a `Set<number>` (from `fleaflickerId: number` in
`teams.ts`), and the boxscore endpoint's `away.id`/`home.id` come back
as strings — `"1434157"`, not `1434157`. A JS `Set.has()` check is
strict-typed, so `knownIds.has("1434157")` silently returns `false`
even though the value is exactly right. Every team-id lookup failed
this way, so every game's points got silently dropped.

Worth noting: the SAME kind of id comparison in this file's scoreboard-
based game discovery (`knownIds.has(g?.away?.id)`) was never touched,
because it's already proven correct — `compute-league-history.ts` uses
the identical pattern against the identical scoreboard endpoint and
produces real results. This mismatch is specific to how the boxscore
endpoint happens to serialize `away.id`/`home.id`, not a general
problem with this project's id-matching approach.

Fixed by coercing with `Number()` at the exact point of comparison,
which is safe regardless of which type Fleaflicker actually sends for
a given endpoint — verified the exact failure and the fix against a
simulated string-id boxscore before shipping.

## The real root cause of the entire top-scorers saga: a silent execution timeout

Every fix in this file up to this point was a real, legitimate bug —
wrong field nesting (twice), a string/number mismatch, a caching layer
serving stale HTTP responses. But none of them could ever have mattered
on their own, because of something more fundamental: this endpoint
makes 700+ external requests across 9 seasons in a single run, and
Vercel serverless functions have a hard execution time limit (10
seconds by default). The function was almost certainly being killed by
the platform before it ever reached the line that saves to Redis — so
no code fix inside that function could ever take effect, no matter how
correct it was. This is why a brand new deployment, brand new repo,
brand new everything still showed the exact same untouched value:
nothing had ever actually finished a full run.

**Fixed at the actual root, two ways:**
1. `vercel.json` now sets `maxDuration: 60` for both compute endpoints
   — the maximum allowed without a paid Vercel plan.
2. `compute-top-scorers.ts` was rebuilt to process **one season per
   call** instead of all nine at once. Each visit merges that season's
   player totals into a running tally (`ftfl:top-scorers-raw`) and
   recomputes the public summary from it. Visiting the URL repeatedly
   advances one season at a time — a single season is ~30-80 requests,
   comfortably within any time limit, so this cannot silently time out
   again regardless of how slow Fleaflicker's API is on a given day.

**To use:** visit `/api/compute-top-scorers` once per season — 9 times
total (2018 through 2026) — checking the response each time for
`seasonsRemaining` and `complete`. Once `complete: true`, every team
page will show real data. Add `?reset=1` to wipe progress and start
over if needed.

## vercel.json: also fixed a platform-level caching override

Separately: `/api/top-scorers` was returning `304 Not Modified` with
`Cache-Control: public, max-age=0, must-revalidate` in the browser,
even though the code explicitly sets `no-store`. Vercel's platform was
overriding the in-function header. Fixed by setting the header at the
`vercel.json` config level instead, which takes precedence:
`/api/(.*)` now gets `no-store, no-cache, must-revalidate, max-age=0`
enforced regardless of what any individual function sets.

## Automatic retry for Fleaflicker rate limits

## Cuts kept re-appearing after being confirmed — real UX bug, fixed
